# Barangay VMS — Full System Capabilities Reference

> **2026-10-07 simplification.** The system now runs on one rule: **one problem → one maintenance ticket → one approval → one repair → one verification → one closure.** Issue Reports, the Custodian inspection step, the Admin "confirm" step, sub-issue lists, manual Maintenance Records, manual Location Records and ticket delete/archive/restore were removed as user-facing workflows (their historical data is kept). Anything below that still describes those is superseded by §§4–7.

**Sidebars now:** Admin — Dashboard; Fleet (Vehicles, Vehicle Types, Vehicle Location); Maintenance (Maintenance Tickets, Maintenance Schedule); Administration (Users, Reports, Activity Log). Custodian — Dashboard, Vehicles, My Work (To Verify / My Tickets, with *Propose Ticket*). Maintenance Personnel — Dashboard, My Work (work orders plus their assigned scheduled work on one page), Vehicles. Super Admin — its own platform portal (§12). Checks, history, documents and usage live on the vehicle profile, not in the sidebar.

A complete, code-verified catalog of everything the system can do today, organized by module. Every capability listed here was confirmed directly against the current codebase (not assumed) — where something is partially built, unused, or a known gap, it's flagged explicitly rather than glossed over. See `Documentation.md` in this folder for the shorter architectural overview; this document goes deep on every feature.

---

## 1. Roles

| Role | Scope | One-line summary |
|---|---|---|
| **Admin** | One Barangay | Review → Approve & Assign → Monitor. Runs the fleet; never reports a problem or creates a ticket. |
| **Custodian** | One Barangay | Propose → Verify. The only role that creates a ticket (by proposing it) and the one who verifies the repair, which closes it. |
| **Maintenance Personnel** | One Barangay | Do the assigned work. Never creates, recommends or reports anything. |
| **Super Admin** | Platform-wide | Account/platform administration only — **no access to fleet data** (vehicles, tickets) at all; enforced server-side, not just hidden in the UI. |
A user can hold more than one of the three barangay roles at once (a "dual-hat" account, e.g. Custodian + Maintenance Personnel in a small barangay). Every permission check ORs across every role an account holds, and several workflow guards (most notably self-verification) specifically account for dual-hat accounts rather than assuming one person = one role.

## 2. Registration & Onboarding

- Public registration requires a **Staff Registration Code**, unique per barangay, validated server-side with a constant-time comparison (`hash_equals`), case-insensitive and trimmed. Codes auto-generate (8 random uppercase characters) the first time a barangay is referenced and can be regenerated by that barangay's Admin (or by Super Admin).
- Registering for a brand-new barangay (one with no staff yet) auto-assigns the registrant as that barangay's **Admin** — no role picker shown. Everyone else must choose **Custodian** or **Maintenance Personnel**.
- **Every** new account starts inactive, including that first Admin — nobody goes live instantly. Approval routes differently depending on who's approving:
  - A barangay's first-ever Admin → approved by a **Super Admin**, from a platform-wide Pending Approvals queue (Super Admins are notified automatically when this happens).
  - Everyone else → approved by that barangay's own existing Admin, who is notified automatically.
- The whole registration (code check + first-registrant detection) runs inside a database transaction with a row lock on the barangay, specifically to prevent two concurrent registrants from a race where both become "first."
- Login for a not-yet-approved or deactivated account shows a message that distinguishes "never approved, waiting on Super Admin," "waiting on your barangay's Admin," and "previously approved, now deactivated."

## 3. Vehicle & Fleet Management

### 3.1 Vehicle Management

**Registration** (Admin always; a Custodian only if an Admin has specifically granted them "Vehicle Registration" on their account — a real per-account toggle on the Edit User form, not a blanket role grant) is a 3-step wizard:
1. **Basic Information** — Land/Water domain (asked first, drives the rest of the form), Vehicle Name, Plate Number (labeled "Registration/Hull No." for Water), Vehicle Type (a creatable dropdown — a new type can be added inline without leaving the form).
2. **Specs** — Brand, Model, Year, Capacity (with unit — kg/tons/L/pax for Land, L/gal/m³/pax for Water), Acquisition Cost (optional — feeds the Reliability card's decommission signal, §9.7), Color, Fuel Type; Water vehicles additionally require Hull Material (Fiberglass/Aluminum/Steel/Wood/Rubber-Inflatable) and Engine Type. Any **custom fields** an Admin defined for the chosen Vehicle Type (§3.2) appear at the end of this step and are validated server-side.
3. **Photo & Location** — an optional photo (≤4MB), Current Location (tied into the hub system, with a live map preview as you pick/create a hub), and optional Remarks.

New vehicles start at status **Available**, condition **Good**. Registration has no document upload — documents are added from the vehicle's own profile (§3.4).

**Import Vehicle Data** (Admin, and a Custodian with the same Vehicle Registration grant — it is registration in bulk, so that gate still applies; Maintenance Personnel cannot import): an Import button on the Vehicles list opens a wizard — download an Excel or CSV template (columns for every Add Vehicle field plus a column per active custom field, with an Instructions sheet of valid Vehicle Types/Locations/Hull Materials) → upload → **preview with nothing saved** ("N valid / N errors / N warnings", each with its row and field, plus a downloadable CSV error report) → confirm → valid rows are imported in one database transaction and invalid rows are skipped → summary. Every row goes through the *same* validation rules the Add Vehicle form uses (shared in `FleetController::vehicleRules`), duplicate plates are caught both within the file and against the database, and the barangay is always the importer's own — no cross-barangay imports. The upload is checked for extension **and** real file contents (≤2 MB, ≤500 rows), cells starting with `=` are rejected, and confirming re-reads and re-validates the stored file rather than trusting rows sent back by the browser. Each import is recorded (who, when, file name, total/imported/failed/warning counts) and writes one Activity Log entry plus a "Vehicle Added" history entry per vehicle.

**Operational criticality** (Critical / High / Normal): each Vehicle Type has a default; an Admin can override it per vehicle (or choose *Inherit* to return to the default). A Custodian cannot set it at registration. It ranks the readiness watch (§9).

**Editing** (Admin only) reuses the same field set; blanking an optional custom field clears its stored value. Changing Current Location through the edit form also writes a location-history record automatically, same as the dedicated "set location" flow.

**Archiving** ("Deactivate" in the UI) sets a vehicle Inactive; **Decommissioning** is a documented end-of-life retirement requiring a written reason, setting it Decommissioned/Needs Repair. Both are blocked while the vehicle has any open (non-Closed/Cancelled) ticket. **Restoring** (from either Inactive or Decommissioned) brings a vehicle back to Available/Good and clears the archive/decommission fields; the same action is relabeled "Recommission" when shown for a Decommissioned vehicle.

**Statuses**: Available, Under Maintenance, Inactive, Decommissioned. (A fifth status, "In Use," exists in the database but is deliberately never set anywhere — the system tracks *availability*, not live dispatch.) Status is mostly system-driven: a failed condition check, an active issue report, or an active ticket automatically flips a vehicle between Available and Under Maintenance. Admin/Custodian can also force a vehicle back to Available via a readiness-check shortcut even with a lingering repair flag — deliberate, since physical readiness and an outstanding paperwork flag are tracked independently.

**Conditions**: Good, Needs Inspection, Needs Repair — driven by condition checks or a ticket moving into maintenance. A retired vehicle (Inactive/Decommissioned) is explicitly protected from having any of this un-retire it.

**Vehicle Profile page** is a single dashboard-style layout (not tabs): Vehicle Information, Status & Key Dates (availability/condition/readiness badges, current location, estimated return date), a Reports card (print a Vehicle Summary Report), a Files card (documents, §3.4), a single-pin location map, a **Usage** card (Admin and Custodian — a vehicle reads **At Base** or **Currently Out**. *Take Out* records purpose/destination/driver and is only possible while the vehicle is Available **and** verified Ready; *Mark Returned* closes it. It writes history and Activity Log entries but never changes the vehicle's fleet status, and there is no odometer), and a **History** card (one timeline with All / Maintenance / Condition / Readiness / Location / Usage filters), and role-gated header actions (Edit — Admin; Readiness Check — Custodian; **Propose Maintenance** and **Condition Check** — Custodian; Decommission/Recommission — Admin).

### 3.2 Vehicle Types

A Vehicle Type captures a unique name, a Domain (Land/Water, required), a **default operational criticality** (Critical/High/Normal), and an optional description. It can also carry Admin-defined **custom fields** — field name, type (Text, Number, Dropdown, Date, Yes/No), required or not, an optional unit, dropdown options and display order — managed from the Edit Vehicle Type page. Fields are **archived, never deleted**: an archived field stops being asked for, but vehicles keep the values they hold (and the profile still shows them); a field's type is fixed once created so stored values stay valid. Values are stored per vehicle and validated server-side on add, edit and import. Fully Admin-only CRUD; deletion is blocked while any vehicle (in any barangay) still references the type. Domain is what makes a vehicle "Water" for every Hull Material/Engine Type requirement elsewhere in the system, and it also relabels fields (Plate Number → "Registration/Hull No.") and changes the capacity-unit choices offered.

### 3.3 Vehicle Location

One module, two tabs:

- **Vehicles Map** — a Leaflet map of named, lat/lng-pinned **hubs** shared barangay-wide, with vehicles grouped onto the hub matching their `current_location`. Features: Map/Satellite basemap toggle (Esri imagery, no API key needed), a service-area boundary overlay (a real barangay boundary where one's on file, falling back to a hardcoded default), Add Hub (click-to-pin with reverse-geocoded address, or type exact coordinates), Remove Hub (default hubs can only be hidden/restored, custom hubs can be truly deleted if no vehicle points at them), focus-on-a-specific-vehicle flyto, fullscreen mode, and **Download Map** — captures the live map (tiles, pins, boundary) to a PNG file, excluding UI chrome from the image.
- **Vehicle Location Record** — a plain tabular history of every recorded location change, filterable by status/location, searchable, with its own Add/Edit flow.

### 3.4 Vehicle Documents

A per-vehicle file cabinet, separate from the vehicle's cover photo — Title (required), Category (free text), File (jpg/jpeg/png/pdf/doc/docx, ≤10MB). Admin can manage any document; Custodian can upload and edit only documents **they personally uploaded**; delete is Admin-only. **Maintenance Personnel can view documents and upload repair evidence** (they edit only their own uploads; they cannot delete — a 2026-10-06 spec decision that reversed the earlier no-access rule). Documents live **only in the vehicle profile** — a compact card expandable into a full table; the separate cross-vehicle "Vehicle Documents" sidebar page was removed.

### 3.5 Vehicle History

One automatic timeline per vehicle, shown on the vehicle profile — there is no manual "add a history entry" and no separate Maintenance History, Records or Location Record screen. The backend writes an entry on nearly every vehicle-affecting action (added, updated, location changed, archived/restored/decommissioned, ticket approved/closed, part removed for another vehicle's repair, readiness and condition checks, taken out/returned, imported). Maintenance, Condition, Readiness, Location and Usage are simply **filters over this one timeline**. Available to Admin and Custodian.

### 3.6 Condition & Readiness Checks (on the vehicle)

A Custodian's quick, proactive "how does it look today" note — **Condition Check** (Good / Needs Inspection / Needs Repair + observations) — is recorded from the vehicle profile; there is no separate Condition Monitoring screen. Anything other than Good offers **Propose Maintenance** immediately, pre-filled from the check. A "Needs Repair" result flips the vehicle Under Maintenance. Only the Custodian records a check (and may edit only their own); Admin may delete a mistaken one.
### 3.7 Readiness Checks

A pre-deployment "is this vehicle mission-ready right now" checklist, deliberately independent of repair/condition status (a vehicle can be Available with a lingering Needs Repair flag and still pass readiness). The checklist is type-specific: Water vehicles get fuel/life-vests/bilge-pump/no-hull-water items; an "ambulance" category gets fuel/oxygen/lights-siren/stretcher; a "fire" category gets fuel/water-tank/pump/hoses/lights-siren; everything else gets a generic fuel/lights/engine-starts set — custom items can be added, and there's a "Mark all OK" bulk toggle. Any single failed item fails the whole check.

Recorded by Custodian only. A passing check is only considered **fresh for 24 hours** — after that it's "stale" even though it passed. States shown: ready, stale, not_ready, unchecked, in_maintenance, retired. A fresh pass on a non-Available vehicle with no open ticket offers a one-click "Mark Available" shortcut (Admin + Custodian) — deliberately does not clear an unrelated Needs Repair condition flag. Surfaces on the vehicle profile, the main vehicle list, both dashboards, and a per-vehicle history of the last 5 checks.

## 4. Proposing Maintenance (replaces Issue Reporting)

There is no Issue Report. When something is wrong, a **Custodian proposes a maintenance ticket** — the problem *is* the form: vehicle, what is wrong, maintenance type, details, priority and an optional suggested mechanic. Entry points, all landing on the same pre-filled form: the vehicle profile's **Propose Maintenance**, the **Propose Ticket** button in *My Work*, a **Condition Check** that isn't Good, and a **due Maintenance Schedule's** notification. One ticket holds exactly one job; a second problem is a second ticket (a proposal with more than one problem is rejected). The server builds the ticket title (`MT-0010 — <Vehicle> — <Issue>`); nobody types it. Maintenance Personnel and Admin cannot propose, report or "recommend" — the Custodian is the single door into maintenance.

## 5. Maintenance Ticket Workflow

```
Custodian proposes ─▶ Admin approves + assigns ─▶ Maintenance repairs ─▶ Custodian verifies ─▶ Closed
   (Pending Approval)        (Active)                (Under Repair)        (verification = close)
```

**5.1 Proposal.** Pending Approval; nothing about the vehicle changes yet. Duplicate protection (same vehicle, same open issue) and recurrence detection (same fault again within 90 days) still apply and are shown to the Admin.

**5.2 Review & Assign (Admin).** One screen: the problem, maintenance type, priority, details — and **who will do the work**. *Approve & Assign* is a single action: the ticket goes Active, the vehicle goes Under Maintenance, and the mechanic receives the work order. A mechanic is required to approve. Declining needs a reason and permanently removes the proposal (the decline is kept in the Activity Log). If the vehicle is currently recorded as Out, the Admin is warned (non-blocking).

**5.3 Repair (Maintenance Personnel).** The assigned mechanic logs the repair (notes, parts, cost, dates, optional photo). The repair method is chosen here, not at proposal: **in-house**, **using a part from another vehicle** (donor part, quantity, condition, reason, date installed — an Admin approves it before the part is removed, and the donor is flagged *Needs Inspection* with a history entry), or **sent to an outside shop** (mark *sent* with shop/reason/scope/estimate, then *returned* with the result/actual cost/warranty — the repair cannot be submitted while it is still out). The Admin may reassign a mechanic (with a reason) or the ticket's Custodian.

**5.4 Verification = closure (Custodian).** The Custodian runs the type-specific functional test, attests they actually operated the vehicle, and approves or rejects. **Approving is the final sign-off: the job becomes Done, the ticket closes, the vehicle returns to Available, a Maintenance Record is written automatically, and Admin is notified.** Rejecting sends it back to the mechanic. Nobody verifies their own repair (a dual-role account that did the work cannot verify it; the ticket must be reassigned to another Custodian). There is no separate Admin confirmation, no decision-close, and no deferral.

**5.5 Cancellation.** An Admin may cancel a ticket before it is closed (this also cancels the schedule it came from). A Closed ticket is locked: it cannot be cancelled, deleted, restored or reopened. There is no ticket delete, archive browser or restore.

**5.6 Existing data.** Tickets that were waiting on the old Admin confirmation were settled automatically by migration (verified repairs became Done and fully-resolved tickets closed). Old issue reports, maintenance records and location records remain in the database; they simply have no screens.

## 6. Maintenance Schedules

Admin creates and edits schedules (vehicle, maintenance type, date/time, location, notes, assignee, optional 1–60-month recurrence) with the same non-blocking conflict warnings as before; Admin also reassigns, cancels and restores. Custodians no longer see or suggest schedules.

**A due schedule never creates a ticket by itself.** A daily job notifies the barangay's Custodians **once** that it is due; the notification opens *Propose Ticket* pre-filled from the schedule (vehicle, type, description, suggested mechanic, `schedule_id`). Submitting links the schedule to that ticket — a schedule can become only one ticket — and from then on it follows the normal flow. Closing the ticket completes the schedule and, for a recurring one, seeds the next occurrence (month-end safe). Cancelling the ticket cancels the schedule. A schedule that already became a ticket cannot also be "completed" directly. The assigned Maintenance Personnel marks stand-alone schedule work done, which creates a record that the Custodian verifies.

---

## 7. Maintenance Records

There is no manual Maintenance Records screen or entry form any more. The ledger is written **automatically** when a ticket is verified/closed or a schedule is completed, and it surfaces through the vehicle's History and the Reports module. Existing manual records are preserved read-only.

## 8. Notifications

**The mechanism itself**: every user has an in-app notification list (latest 50), can mark one or all as read, and can delete one. Clicking a notification opens the exact ticket, vehicle, or (for a due schedule) a pre-filled Propose Ticket form it's about (not just a generic dashboard) whenever one is linked to it. Old notifications are pruned automatically by a **daily scheduled job** — a read notification is removed after 30 days, and anything (read or not) is removed after 90 days regardless.

**What triggers one, and who gets it** — every distinct event found wired to a notification across the ticket/issue/schedule workflow:

| Event | Recipient |
|---|---|
| Custodian proposes a ticket | Barangay Admins |
| Admin approves & assigns a proposal | The proposing Custodian + the assigned mechanic |
| Admin declines a proposal | The proposing Custodian |
| A mechanic is reassigned / the ticket's Custodian is reassigned | The new (and previous) person |
| A repair is logged and ready to verify | The assigned Custodian |
| A cannibalized repair is submitted / approved / rejected | Barangay Admins, then the mechanic |
| A verification passes | (ticket closes) Barangay Admins + the mechanic(s) |
| A verification fails | The mechanic |
| A due schedule | The barangay's Custodians (opens Propose Ticket pre-filled) || A recurring fault is detected | Barangay Admins |
| A non-Admin self-files a maintenance record | Barangay Admins |
| A maintenance record is decision-closed without verification | Barangay Custodians |
| A schedule is created/edited/reassigned/restored with an assignee | That assignee (+ the previous one, on reassignment) |

## 9. Fleet Intelligence & Dashboard

All computed live on every dashboard load — there is no caching or scheduled pre-computation for these numbers:

1. **Readiness & Coverage** — per-vehicle-type counts (total / ready / verified-ready / down), flagging a vehicle type with zero ready units as having no coverage at all.
2. **Availability Forecast** (Admin) — every vehicle currently under maintenance with its expected return date, soonest first.
3. **Preventive-maintenance-due watch** — schedules due within 7 days or already overdue.
4. **Readiness watch** — vehicles that are "Available" on paper but not actually *verified* ready (stale, failed, or never-checked).
5. **Single-point-of-failure detection** — any vehicle type down to one (or zero, flagged critical) ready unit.
6. **Fleet-wide failure-pattern detection** — the last 12 months of maintenance grouped by type, surfacing a systemic recurring cause rather than isolated incidents.
7. **Per-vehicle reliability lens** — failure counts, average days out of service, lifetime repair spend, a "chronic" flag, and a decommission signal when lifetime repair spend nears acquisition cost. Shown as a "Reliability" card on the Vehicle Profile page, visible to Admin.
8. **Action Queue** (Admin) — one ranked worklist combining proposals awaiting review, jobs with no mechanic, readiness-check gaps, overdue schedules, and recurring-fault reviews.
9. **My Scheduled Work** (Maintenance Personnel) — that mechanic's own upcoming assigned schedules.
10. **Sole-active-Admin warning** — proactively flags an Admin if they're the only one left for their barangay, before anyone tries to deactivate/demote them (the guard itself is described in §11.2).
11. Supporting KPI tiles and charts: fleet counts by status, by type, by location, by condition; total maintenance spend; a recent-activity feed; role-tailored metric subsets (Admin gets the full operational/financial picture; Custodian gets issue-centric counts; Maintenance Personnel gets repair/schedule-centric counts plus a "vehicles needing attention" list).
12. **Fleet Capability & Readiness Impact** — the per-vehicle Criticality Watch (below) rolled up to the Vehicle Type level, answering "what emergency capability is at risk right now?" rather than "which vehicle." Each affected type gets a coverage state — `COVERED` (not shown — only affected types are listed), `LIMITED` (ready units exist, but something's down), `AT_RISK` (down to its last ready unit — agrees with the single-point-of-failure flag above), or `NO_COVERAGE` (zero ready units) — plus the type's highest effective criticality, a primary reason, the specific affected vehicles, and a link to each one's active ticket when one exists. Built entirely from the same `responseReadinessState`/`effectiveCriticality` primitives as everything else here — no second algorithm. Shown as a dashboard card (Custodian/Maintenance Personnel) or inside Risk & Readiness Watch (Admin).

---

### 9.x Fleet Readiness & Criticality Watch

One list of every operational vehicle that is **not** currently verified ready — in maintenance, failed readiness check, never checked, or check out of date — ranked **Critical → High → Normal** using each vehicle's effective criticality (§3.1). It reuses the single readiness rule used everywhere else (`responseReadinessState`), so the watch can never disagree with the vehicle profile. Admins see it inside Risk & Readiness Watch; Custodians and Maintenance Personnel see it as a dashboard card.

## 10. Reports

Seven report types, Admin-only: Vehicle Inventory, Vehicle Type, Vehicle Location, Vehicle Issue, Vehicle Maintenance, Vehicle Maintenance Schedule, and Vehicle History — each filterable by its own relevant fields (category, location, issue type/severity, maintenance type/date range, etc.). Preview renders in-browser; "print" uses the browser's native print rather than a generated PDF. CSV export is available for the report output itself and separately for the vehicle list, user list, schedules, vehicle history, the work tracker, and activity-log breakdowns. Every report generation is itself logged to the Activity Log.

## 11. Users & Administration

### 11.1 User management (barangay-scoped, by that barangay's Admin)

List/search/filter users, create a user (barangay is forced server-side to the Admin's own — can't be spoofed), edit, activate (can also confirm/override the requested role on first approval), and deactivate (which immediately revokes every one of that user's active login tokens, not just a flag flip). View or regenerate the barangay's registration code. For a Custodian specifically, the Edit User form also has a "Vehicle Registration" toggle — grants or revokes that one account's ability to register a vehicle (§3.1), independent of the Custodian role itself. Every one of these actions — create, edit (including role changes and password resets, without ever logging the password itself), activate, deactivate, and the registration-delegation toggle — writes an Activity Log entry.

**Last-Admin protection**: blocks deactivating, or removing the Admin role from, a barangay's only active Admin — with a clear explanation of why, naming the account and asking that someone else be promoted first. This does **not** prevent a sole Admin from simply walking away with no successor promoted; that specific recovery case is what the Super Admin's platform-level role-change tool exists for.

**Open-work protection**: separately, nobody can be deactivated while they still have open work assigned to them — an open ticket as Custodian, an unfinished sub-issue as mechanic, or a Scheduled maintenance entry — the system lists exactly what needs reassigning first. Nobody can deactivate their own account.

### 11.2 Authentication

Token-based (Sanctum), no server-side session state. Login and password-change are both rate-limited against brute-forcing. Tokens are tagged with every role an account holds, and carry a computed ability list the frontend uses to decide what to show. A changed password requires the current one to be verified first. Tokens expire after 7 days by default (configurable). **There is no self-service "forgot password" flow** — confirmed absent, not just unverified; recovery is entirely through an Admin editing the account.

A deactivated account's existing token stops working on its very next request, not just at the next login attempt.

### 11.3 Impersonation

A support/testing tool, gated two different ways depending on who's using it: for an Admin, it's **dev-only** (returns a flat 404 outside a local/testing environment — it doesn't exist in a deployed app for this role). For a Super Admin, it's a real production account-recovery path. Either way requires a written reason (logged) and is fully blocked from targeting another Super Admin. Outside local development, an active impersonation session is **read-only** — every state-changing request is refused except logging out or switching/ending the impersonation itself — and the session token expires after 30 minutes. Starting and ending an impersonation are both logged.

### 11.4 Activity Log

Every logged action records who did it, **which specific role/function they were acting under** (not just their primary role — so a dual-hat account's action is attributed correctly), what the action was, what module and record it affected, and a free-text detail sentence. A barangay's own Admin sees their full operational log (vehicles, tickets, issues, everything), filterable and searchable. The platform-wide Super Admin log is deliberately restricted to account-level activity only (registrations, approvals, impersonation, profile changes) — fleet-detail entries never leak through that view.

## 12. Super Admin Platform Portal

Entirely separate from the three barangay roles, and **explicitly barred from all fleet data** by a server-side allowlist middleware — not a UI convention, a hard block that 403s any attempt to reach a vehicle/ticket/issue/maintenance endpoint.

Capabilities: list every barangay (with staff counts, whether it has an active Admin, registration code, and boundary status) and create new ones; view/regenerate any barangay's registration code (showing when it was last changed); look up a missing boundary against a public geocoder (a real, working feature, though coverage isn't guaranteed for every barangay); approve pending registrations platform-wide, now behind an explicit confirmation step naming the account and barangay — and flagging distinctly when it's a brand-new barangay's first Admin, since that's specifically what activates it (final stabilization, 2026-10-11, since this previously fired on one click, asymmetric with Reject which already confirmed); activate/deactivate any user system-wide (subject to the same last-Admin and open-work guards as barangay-level deactivation); permanently reject a still-pending (never-approved) registration; change any user's role platform-wide — including recovering an Admin-less barangay by promoting someone already there; view, resolve, reopen, or permanently delete publicly-submitted **Concern Reports** (unauthenticated "something's wrong with a barangay's account" submissions from the Support page); and view the platform-wide, account-only activity log.

**Boundary review workflow** (final stabilization, 2026-10-11): a boundary match from the geocoder is never auto-saved. It lands as a candidate awaiting review — shown as a **Needs Review** badge in Barangay Management (a dashboard KPI card and filter tab surface these across the whole platform) — which opens a real map preview of the matched polygon before a Super Admin explicitly **Confirms** it (writing it as the barangay's official boundary, stamped with who/when/source) or **Discards** it. Three real states exist: **Verified** (confirmed and on file — all pre-existing boundary data was backfilled into this state so it doesn't suddenly look unreviewed), **Needs Review** (a found-but-unconfirmed candidate), and **Not Found** (the geocoder returned nothing usable — includes a geometry sanity check that rejects a degenerate or unclosed polygon before it's even offered for review). An already-verified boundary can never be silently overwritten by a later lookup — the refresh endpoint refuses to touch one once confirmed.

## 13. Security Posture

- Token auth (Sanctum) with no server-side session state; CORS restricted to a single configured frontend origin.
- Rate limiting on login, registration, registration-status checks, concern-report submission, and password changes.
- Input sanitization strips control characters globally (deliberately does **not** strip HTML — the actual XSS defense is React's own output-escaping, not input mangling).
- A full set of security headers on every response (clickjacking, MIME-sniffing, referrer, permissions-policy, and a restrictive Content-Security-Policy), plus removal of headers that would advertise the tech stack.
- No raw/interpolated SQL — all queries go through parameterized Eloquent/query-builder calls.
- Every controller action enforces a specific permission ability against a single source-of-truth role→ability map before doing anything; ownership and live-state rules (own record only, not-the-repairer, same barangay, last-Admin) are layered on top as separate, explicit checks rather than folded into that map.
- A deactivated account's token dies immediately on its next request, independent of its stated expiry.
- **Cross-barangay access is blocked structurally, not just by convention**: `Vehicle` (and models hanging off it, like its documents and location history) carries a global `BelongsToBarangay` query scope, so route-model binding itself 404s before a controller even runs if the requested record belongs to a different barangay — confirmed in the final stabilization pass by direct code review, not assumed from the permission map alone.

## 14. Known Gaps & Partially-Built Items

Stated plainly, as found in the code — not implied to be bugs, just not (yet) user-facing or fully wired:

- **No self-service password reset.** Entirely by Admin edit; the reset action is logged, but nothing forces the user to change it on next login — a deliberate scope decision for now, not an oversight.
- **"In Use" vehicle status** exists in the database but is never set by any code path — dispatch state isn't tracked, only availability.
- **File storage is bucket-public by design** — vehicle documents, issue attachments, and repair photos are reachable by anyone holding the exact (non-sequential, not browsable) generated URL, with no per-request authentication. A documented, deliberate trade-off, not an oversight — see the code comment on `config/filesystems.php`'s `'public'` visibility setting.
- The **last-Admin protection** stops specific actions (deactivate, remove Admin role, platform role change) but doesn't prevent every conceivable way a barangay could end up without an active Admin — the Super Admin recovery tool exists specifically to fix that case after the fact, not to make it impossible in advance.
- **Import / custom-field limits:** an import takes at most 500 rows / 2 MB per file; custom fields are per Vehicle Type (a template column per distinct label), and the import template does not yet include a per-row hull/engine hint beyond the Instructions sheet.
- **Usage is an indicator, not dispatch** — it records a checkout and return (no GPS, trips or odometer). It only gates *Take Out* (Available + Ready); it never changes the fleet status.
- **Barangay boundary lookup** depends on a public third-party geocoder with no guaranteed coverage — a legitimate "no boundary found" result is expected for some barangays, not a bug.
